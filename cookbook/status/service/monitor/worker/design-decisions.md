
- **Decision**: validate only that `workerData.storage` or `workerData.db.url`, and `workerData.config`, are present/truthy at boot, not their full shape or validity.
  **Rationale**: the source's own comment states this narrowly, on purpose: "Fail fast on a malformed spawn rather than surfacing a confusing crash deep inside `openLibsql`/`runMonitorCycle`: `db`/`config` are the two things the client MUST supply (and, in current source, a `storage` port stands in for `db`) (see `MonitorWorkerData`) and a missing one means the client itself is broken." A malformed-but-present value (a syntactically invalid URL, a config object missing an unrelated optional field) is deliberately left to surface later — inside `openLibsql`/`tuneDbForConcurrency`/`connectStorage` at boot, or inside a cycle's own `try`/`catch` — rather than this file attempting deeper validation of a shape `MonitorWorkerData`'s type already documents.
  **Approved**: pending
- **Decision**: fire-and-forget each cycle's async work from the `message` handler rather than queueing or awaiting a previous cycle before starting the next.
  **Rationale**: the only spawner of this module in this codebase, `MonitorWorkerClient`, never posts a second `CycleRequest` before the first's `CycleReply` arrives — the scheduler's own single-flight `tick()` (external, per the sibling Status Server Monitor Cycle Runner recipe's Concurrent Access analysis) keeps exactly one cycle outstanding system-wide. Adding a queue or lock here would duplicate a guarantee the caller already provides, for a condition this file never actually encounters in production.
  **Approved**: pending
- **Decision**: run the entire monitoring cycle on a dedicated worker thread, with its own event loop and database access (a transferred storage port or its own connection), rather than in-process on the API thread.
  **Rationale**: the file's own header comment names the incident this fixes directly — heavy full-sync work (four provider APIs, telemetry, TLS handshakes, JSON parsing) starved the API server's event loop, resetting in-flight `/auth/me`/`/auth/refresh` proxy sockets and making `/health` probes read "down," which triggered supervisor container restarts. A dedicated thread with its own event loop removes that starvation path entirely.
  **Approved**: pending
- **Decision**: deliver `conn`/`storage`/`config`/`cooldowns`/`hogqlLock` (including every credential `conn` and `config` carry) exclusively through `worker_threads`' structured-clone `workerData`, never through any other channel this file reads from.
  **Rationale**: `workerData` crosses the thread boundary in-process, never serialized to a command-line argument (world-readable via `ps` for the life of the process) or to a network call. `worker-boot.int.test.ts`'s own driver (`worker-boot-driver.mjs`) delivers the equivalent payload over stdin rather than argv for exactly this reason, by its own comment: "a command-line argument is world-readable through `ps` for the life of the process, and would be echoed back into any error the test throws." This file's single `workerData` destructure is the only read of that boundary.
  **Approved**: pending
- **Decision**: prefer a transferred storage port to the host's database thread over a connection the worker opens itself, keeping the own-connection path as a fallback.
  **Rationale**: with a storage port every database call goes through one thread, so the worker holds no connection of its own and cannot contend with the host for the file; the own-connection path (`openOwnStorage`) remains for a spawner that supplies only `db`. Both paths run once at boot and the resulting `Storage` is reused.
  **Approved**: pending
- **Decision**: adopt the parent's HogQL lease (`attachHogqlLockState`) alongside the provider-cooldown state.
  **Rationale**: this cycle's KPI poll and the API thread's dashboard sections query the same PostHog, and a private lease would let them overlap; sharing one `SharedArrayBuffer` keeps one query in flight across both threads.
  **Approved**: pending
