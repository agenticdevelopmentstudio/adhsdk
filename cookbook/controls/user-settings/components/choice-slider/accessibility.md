
- **Role**: The control MUST have the platform's slider role (on web, the implicit ARIA role `slider` of the range input).
- **Labeling**: If a `label` prop is provided, it MUST be associated with the control (on web, `<label htmlFor={fieldId}>`, where `fieldId` is the `id` prop or the `useId()` fallback). When `label` is omitted, the control MUST still have an accessible name (see **accessible-name**).
- **Keyboard support**: The control MUST support arrow key navigation (left/right to decrease/increase value) per the platform's slider behavior. No additional keyboard handling is required.
- **Screen reader announcement**: The control MUST expose the selected choice's label as its value text (see **aria-valuetext**), so assistive technology announces the label and not the choice index.
- **Touch target size**: The slider thumb's hit area MUST be at least 24×24 CSS px (WCAG 2.5.8 Target Size Minimum). An implementation MUST keep the platform's native thumb, MUST tint it using the `--aws-accent` token, and SHOULD enlarge the hit area with padding if the platform's native default falls short.
- **Known gaps**: The reference implementation (`ChoiceSlider.tsx`, `styles.css`) does not meet three of the items above. It sets no `aria-label`, `aria-labelledby` or `title` when `label` is omitted, so the slider has no accessible name. It sets no `aria-valuetext`, so assistive technology announces the index (`0` through `choices.length - 1`); the caption is a sibling of the input and is not related to it by `aria-describedby` or `aria-labelledby`. It declares no thumb size, so the thumb is the browser's native size, which varies and may be under 24×24 CSS px. These are the reasons for the `partial` compliance rows.
